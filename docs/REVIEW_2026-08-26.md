## Findings

Ordered roughly most- to least-severe. Each includes what was actually done

### 1. Suspected deadlock on the abort path — **fixed**

`cmd_LOAD_ABORT` and `cmd_UNLOAD_ABORT` (`klippy/extras/buffer_manager.py`)
are registered as `gcode.register_mux_command` handlers, which Klipper
dispatches while holding `gcode.mutex`. Both called `self._stop_lane()`
inline, which calls `backend.stop()` → `LllBufferBackend.stop()` →
`self.gcode.run_script(...)` — and `run_script` itself takes `gcode.mutex`.
Klipper's gcode mutex is a reactor mutex, not reentrant: re-acquiring it from
the same greenlet that already holds it blocks forever.

By contrast, `jog()`/`run()` use `run_script_from_command` (no mutex), and
`_stop_lane()`'s other four callers (`_fail_load`, the phase A→B and B→C
handoffs, `_stop_then_unloaded`/`_stop_then_unload_failed`) all run inside a
`reactor.register_callback` greenlet that does **not** hold the mutex — for
those, `run_script`'s mutex protection is correct and intentional (it
serializes the stop against other concurrently-dispatched gcode).

**Fix applied**: left `backend.stop()` and its four safe callers alone, and
changed only `cmd_LOAD_ABORT`/`cmd_UNLOAD_ABORT` to defer the stop via
`self.reactor.register_callback(lambda et: self._stop_lane())` — the same
idiom the file already uses everywhere else a lane-stop needs to run actual
gcode. This is a source-inspection fix based on how Klipper's `gcode.mutex`
is documented to behave; it has **not** been exercised against a live
Klipper instance. Worth a deliberate bench test: arm a load, then send
`BUFFER_LOAD_ABORT` and confirm it returns promptly instead of hanging the
command queue.

### 2. Extrude-move triplication — **fixed**

Three sites (`_run_phase_b`, `_run_unload_retract`, `_run_unload_clear`) each
independently read `gcode_move`'s `absolute_extrude` status, built an
`M83 / G1 E<mm> F<speed> / M400 [/ M82]` script string, and called
`gcode.run_script`. Extracted into one helper, `_extrude(gcode_move, mm,
speed_mm_min)`; each call site keeps its own `try/except` (the failure
messages differ per phase, which is the reason not to swallow exceptions
inside the helper too). Verified the three call sites now produce the same
gcode as before (same format strings, same `M82` gating logic, negative `mm`
for the two retract sites).

### 3. Dead code — **fixed**

- `pos_before = status.get("position", 0.0)` in `_run_phase_a` was assigned
  and never read (phase A measures via the MDM counter, not Roadrunner
  position — the comment block a few lines below already explains why).
  Removed.
- `MDM_NOT_AVAILABLE = (None, None)` sentinel was never referenced anywhere;
  its own docstring said it exists for "a hypothetical future backend," not
  the one backend that exists today. Removed; `LaneBackend.mdm()`'s
  docstring now spells out the tuple literally instead of naming a constant
  that doesn't exist. Trivial to reintroduce once a second backend actually
  needs it.
- `LOAD_ACTIVE_PHASES` was unused — `_on_error` hand-wrote its two halves as
  separate inline tuples instead of importing the module-level one. Rather
  than deleting the distinction, split it into `LOAD_FALLBACK_PHASES` and
  `LOAD_SENSOR_PHASES` (the two halves genuinely behave differently — one is
  handled by direct-failing off a reactor timer, the other via the
  poll-based `_phase_abort_reason` idiom) and pointed `_on_error` at the
  named tuples instead of its inline literals. One source of truth instead
  of a matching pair that could drift.

### 4. Greenlet-generation hazard on abort → immediate re-begin — **reported only**

If `BUFFER_LOAD_ABORT` fires and `BUFFER_LOAD_BEGIN` is issued again before
the aborted phase A/B greenlet loop has taken its next `_check_phase_abort()`
poll, two loops could be alive briefly: the old one (about to notice
`"aborted"` and return) and the new one just registered. `load_phase` is
reassigned at the top of `cmd_LOAD_BEGIN`, so the old loop's own `if
self.load_phase != PHASE_A_PUSH: return` guard at the top of `_run_phase_a`
would likely catch this in practice — but it's a "likely," not a proof, and
worth a generation counter (`self._load_generation`, incremented on every
`LOAD_BEGIN`/`LOAD_ABORT`, checked alongside the phase) if it's ever seen to
misbehave. Not fixed — didn't want to add unrequested state machinery to a
pipeline that has never run against real hardware, on inference alone.

### 5. `_query_busy` check-then-set race — **reported only**

`lll_buffer.py`'s `_poll`, `cmd_QUERY`, and `probe_arm` all do a non-atomic
read-then-write of `self._query_busy` to avoid two concurrent waiters on the
`lll_state` response. This is safe today only because Klipper's gcode
dispatch and timer callbacks all run on one greenlet at a time cooperatively
— there's no true concurrency to race. Worth a one-line comment recording
that assumption explicitly, so a future change to Klipper's threading model
doesn't reintroduce a real race silently. Not fixed — no bug today, just an
implicit assumption worth naming.

### 6. Hardcoded Moonraker URL — **reported only**

`LLLBuffer._push_active_spool` posts to `http://localhost:7125/server/spoolman/spool_id`
unconditionally. Fine for the single-host reference setup this was built
against; would silently no-op (falling into the caught `Exception` and a log
line) on any setup where Moonraker listens elsewhere. Low priority — not
fixed, since making it configurable is a design decision (new config option,
name, docs) rather than a mechanical cleanup.

### 7. `src/buffer.c:983` unreachable branch — **reported only, no firmware edit**

```c
} else if (func == FUNC_BUTTONS || func == FUNC_MBSIG) {
    if (manual) { ... }
```
`FUNC_MBSIG` is already handled by its own dedicated `if (func ==
FUNC_MBSIG)` branch earlier in the same `if/else if` chain (`command_lll_enable`,
around line 966), so this `else if` can only ever match on `func ==
FUNC_BUTTONS` — the `|| func == FUNC_MBSIG` half is dead. Harmless (it would
just re-run the same cleanup a second time if it were ever reachable), but
worth deleting the stray clause next time this function is touched.
**Not edited** — firmware changes need the Klipper-host build to verify, per
CLAUDE.md; this is flagged for whoever next touches `command_lll_enable`.

### 8. MDM edge-counting cadence — **unquantified, flagged for the bench**

TMC UART writes are bit-banged in `buffer_task` (~8 ms per burst, per the
Mainsail-load-false-positive note in README). During that burst the task is
busy-looping in `tmc_write`/`bit_delay`, not reading GPIO. `mdm_motion_count`
increments by comparing `mdm_motion` against its previous sample once per
task tick — if the MDM's motion pin can toggle and toggle back within one
~8 ms TMC-write burst, that edge is lost. Whether this matters depends on a
number nobody has measured yet: the encoder's edge period at the fastest
filament speed this hardware will actually see, versus 8 ms. Phase A's stall
detection, the learned feed-rate estimate, and T10's differential check all
lean on this counter's fidelity, so it's worth putting a real number on it
once the MDM is wired — not asserting a defect here, since it may well
resolve to "never happens at these speeds."

`experimental/phase-c/buffer.c` (1583 lines) and `lll_buffer.py` (729 lines)
are full copies of the firmware/host pair, kept to preserve a withdrawn

### 4 (was "reported only") — Greenlet-generation hazard: fixed for real

Traced the race further before dismissing it as unlikely, at Vi's
insistence, and found it's real: `cmd_LOAD_BEGIN` resets
`self._phase_abort_reason = None` at its own top, *before* any check that an
old phase A/B greenlet from a just-aborted load has actually consumed the
`"aborted"` sentinel yet. `BUFFER_LOAD_ABORT` immediately followed by
`BUFFER_LOAD_BEGIN` (before the old greenlet's next `reactor.pause()`
wakeup) can leave the old greenlet finding the sentinel already cleared and
`load_phase` already `PHASE_A_PUSH` again (set by the new call) — it keeps
running, concurrently with the new greenlet, both calling `self.backend.jog()`
and mutating `self._learned_feed_mm`/`self._phaseA_stall_streak` etc.

Fixed with two generation counters, `self._load_generation` and
`self._unload_generation` (`klippy/extras/buffer_manager.py`). Each is
incremented at the point a fresh greenlet chain is scheduled
(`cmd_LOAD_BEGIN`/`cmd_UNLOAD`, sensor-pipeline branches) and again on
`cmd_LOAD_ABORT`/`cmd_UNLOAD_ABORT`, so an aborted chain is invalidated
immediately even with nothing new following it. The value is captured **at
the scheduling call site** (bound into a `lambda et, g=gen: ...`), not read
inside the callback body — by the time a greenlet's own first line runs, a
newer call may already have bumped the counter again, so reading it from
inside would defeat the whole check. Threaded through the full chain on both
sides (`_run_phase_a` → `_run_phase_b`; `_run_unload_tip_form` →
`_run_unload_retract` → `_run_unload_clear`), and folded into
`_check_phase_abort`/`_check_unload_abort` so every existing poll point gets
the check for free. A superseded greenlet returns silently (not a failure —
being superseded is the intended outcome of a fresh `LOAD_BEGIN`).

This is additive to `_phase_abort_reason`/`_unload_abort_reason`, not a
replacement — those still distinguish "quiet cancel" from "real failure" for
the *current* generation's own loop.

**Not bench-verified** — this is a source-level fix for a race that was
traced through the code, not reproduced against a live Klipper instance.

### 6 (was "reported only") — Moonraker endpoint: configurable, socket-first

New config option `moonraker_endpoint` (`klippy/extras/lll_buffer.py`),
default `~/printer_data/comms/moonraker.sock`. At call time, an
`http://`/`https://` value uses the existing HTTP POST (now against the
configured base URL instead of the hardcoded `http://localhost:7125`);
anything else is treated as a filesystem path to Moonraker's Unix domain
socket.

Confirmed from Moonraker's own documentation (not assumed): the socket
lives at `<datapath>/comms/moonraker.sock`, speaks JSON-RPC where each
message is UTF-8 JSON terminated by a single ETX (`\x03`) byte, and the
spool-push call is `server.spoolman.post_spool_id` with `{"spool_id": N}`
params — the exact equivalent of the HTTP body this replaces.

**One assumption is not confirmed and is commented as such in the code**:
whether `server.connection.identify` must precede other JSON-RPC calls on a
one-shot (non-persistent-agent) connection isn't documented explicitly
either way. The implementation sends it first anyway, since that's the
documented-safe pattern for a persistent connection and costs one small
extra message if it turns out to be unnecessary. Worth confirming against a
live Moonraker instance before relying on this in production — same
disclosure standard as the rest of this repo's unbenched pipeline code.

Vi asked specifically whether the socket might not exist in every
deployment (older Moonraker, unusual layout, Moonraker not local to the
Klipper host) — yes, which is why this is one configurable value accepting
either shape, defaulting to the socket, rather than hardcoding either
transport.
